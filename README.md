# ACVD Mouse Aim

把《装甲核心：审判日》（Armored Core: Verdict Day）的键鼠操作，
转换为标准 Xbox 手柄输入，运行在 [Xenia Edge](https://github.com/has207/xenia-edge)
模拟器上。

**输入重映射（Input Remapping）与操作体验增强（Control Enhancement）。**
不修改游戏文件，不修改存档，不联网，不收集任何数据。

---

## 它是什么

一个常驻的键鼠 → 虚拟 Xbox 手柄映射程序，外加一套视角跟随控制逻辑。

```
键盘 + 鼠标 ──→ 本程序 ──→ 虚拟手柄 ──→ Xenia ──→ 游戏
```

特色是**鼠标控制视角**：

- 鼠标左右移动 → 视角左右转
- 鼠标上下移动 → 视角俯仰
- 移动多少，视角转多少（和视场角联动，开镜时自动切到高精度）

另外支持完整的键位映射（键盘按键 → 手柄按键 / 摇杆），
带图形化改键界面。

## 快速开始

### 1. 装 ViGEmBus 驱动（只需一次）

下载：https://github.com/nefarius/ViGEmBus/releases

装完**重启电脑**。这是创建虚拟手柄所必需的内核驱动。

### 2. 装 Python 依赖

```batch
pip install vgamepad
```

Python 3.10 或更高。

### 3. 启动

```batch
python tools\mapper.py
```

或者双击 `启动.bat`（会自动找 Python 并打开控制面板）。

### 4. 配置 Xenia

在 Xenia 的控制器设置里：

- 槽位 1 绑定 **Xbox 360 Controller**（也就是虚拟手柄）
- 槽位 1 **不要**同时绑定 Keyboard

配置错了的表现是按键响应两次，或者视角乱动。

## 技术原理

### 为什么用相机朝向而不是瞄准组件坐标

要做出「鼠标指哪看哪」的手感，需要一个能反映「当前视角朝向」的数值。
本作的瞄准系统提供了两个层次的候选数据源：

| 方案 | 问题 |
|---|---|
| 追踪**瞄准组件实例**（准星那个逻辑结构） | 实例地址随配装与运行环境变动，需要动态匹配 |
| 追踪**相机全局朝向** | 地址相对稳定，但存在弹簧臂带来的视觉滞后 |

本项目第一版曾尝试追踪瞄准组件实例，实际遇到两个结构性障碍：

1. **模拟器的动态内存分配机制**会让实例地址在运行期间发生漂移，
   不能当作长期有效的引用。
2. 更关键的是，**不同机体的瞄准配件（头部、躯干）在内存中是完全独立的
   实例对象**。要稳定追踪瞄准组件，等于要把所有配件的对应结构全部
   逐一解析，再写一套复杂的动态匹配规则 —— 换个配装、换台电脑就重来一遍。

于是放弃这条路，改为追踪相机。相机是玩家实体的**全局根组件**，
跨配装相对稳定，也不需要为每种配件单独适配。

```
Target_Abs = 鼠标累加出来的目标方向（360° 环 + 线性俯仰）
Aim_Abs    = 相机的当前朝向
Error      = Target_Abs − Aim_Abs
杆量        = 死区逆变换(Error / 满杆角)
```

代价写在「关于这个项目」一节里：相机有弹簧臂的视觉滞后，
极限微调时鼠标的跟随不是绝对精准。这是一个明确的技术取舍，不是遗漏。

因为相机地址相对稳定，**整条链上没有任何实例搜索动作** ——
没有组件枚举，没有候选池，没有推送验证，没有定位状态机。

### 相机结构布局

从 FOV 地址往回退 0x30 字节是结构起点（大端 float）：

```
-0x30 .. -0x24   世界坐标 xyz（3 × f32）
-0x24 .. -0x20   w 校验位（必须 ≈ 1.0）
-0x20 .. -0x10   朝向四元数 xyz w
-0x10 .. +0x00   缩放（前三个应在 0.5 ~ 2.0）
+0x00            视场角
```

读之前加 guest 基址（通常是 `0x1_0000_0000`）换成宿主地址。

三重校验（w≈1、缩放范围、四元数模长）任一不成立就丢弃这一帧 ——
地址固定不代表内容固定，换关或加载中那块内存可能是别的东西。

### FOV 为什么不能进闭环

`Error` 是世界角度差，跟视场无关。FOV 只用在两处：

1. 输入增益（鼠标像素 → 世界角度）
2. 准星投影（纯显示）

把 FOV 塞进闭环会怎样：冲刺时 FOV 从 50 拉到 70，焦距变化 12%，
如果控制律依赖 FOV，推力会跟着抖。这是实测踩过的坑。

## 代码结构

```
acvd/
  core/                瞄准内核（10 个文件）
    sensor.py            250Hz 读固定相机
    control.py           纯函数：误差 → 摇杆量
    control_v2.py        逆模型去滞后（实验性，默认关闭）
    output.py            125Hz 合成 + 看门狗
    engine.py            装配门面
    types.py             层间契约
    chan.py              Slot / Alarm
    blackbox.py          环形记录，可导出 CSV
    guard.py             AST 分层检查
  focus.py             找 Xenia 窗口
  winmem.py            进程内存读写
  gmem.py              guest → 宿主地址换算
  pad.py               虚拟手柄（ViGEm）
  pipe.py              进程间管道
  keyhook.py           键盘钩子
  mousehook.py         鼠标钩子
  rawmouse.py          Raw Input
  overlay.py           准星窗口
  cursor.py            光标隐藏
  keynames.py          虚拟键码 ↔ 键名
  errors.py            异常类型

tools/
  mapper.py            主程序（输入输出编排）
  panel.py             控制面板 GUI
  keymap_ui.py         按键映射界面
  launch.py            启动器
  rebind.py            命令行改键
  ctl.py               管道客户端
  rebind.py / tune.py  配置工具
```

### 四层解耦

```
sensor   ──Snap──►   Composer   ──OutFrame──►   Watchdog
250Hz 读相机          125Hz 算杆量              100ms 断流强制回中
```

`guard.py` 用 AST 静态分析检查每一层的 import 关系，比如
`control.py` 不许 import `threading`。**违规直接拒绝启动**，不是警告。

为什么值得这么严格：分层最容易不是被「故意破坏」，而是被「顺手」破坏 ——
某天为了省一次拷贝在 controller 里写了个 `time.perf_counter()`，
分层就名存实亡了。

## 配置

### `keymap.json` —— 键位

支持 `//` 注释。改完发管道命令 `reload`，或用图形界面自动重载。

鼠标键写 `mouse_left` / `mouse_right` / `mouse_middle`，
不要写裸的 `left` / `right`（会被当成键盘方向键）。

### `tune.json` —— 手感

| 参数 | 作用 |
|---|---|
| `full_stick_angle` | 误差多少度给满杆。越大越稳但越慢 |
| `game_deadzone` | 游戏自身的摇杆死区（本作实测 0.44） |
| `dead_px` | 准星绿圈半径，单位是**屏幕像素** |
| `curve_gamma` | 响应曲线。1.0 线性，2.0 接近目标自然减速 |

`dead_px` 用像素而不是角度，是因为开镜时 FOV 从 50 压到 10，
同样的角度误差在屏幕上放大 5 倍 —— 用角度做死区会把狙击精度吃掉。

| 键 | 作用 |
|---|---|
| F1 | 重新对齐坐标（换关后按） |
| F2 | 准星归中 |
| F9 | 暂停鼠标闭环（键盘照常） |

## 常见问题

**启动报「创建虚拟手柄失败」**
ViGEmBus 没装，或装完没重启。

**绿准星在，但动鼠标视角不动**
① 不在关卡内（菜单里没有相机数据）
② 按了 F9
③ Xenia 槽位没绑虚拟手柄

**按键响应两次**
Xenia 槽位同时绑了 Keyboard 和虚拟手柄，去掉 Keyboard。

**换关卡后视角猛转**
按一次 F1 重新对齐。正常情况下会自动重锚，如果频繁发生
说明相机位置的跳变阈值需要调整。

## 关于这个项目

本项目为**纯 AI 辅助架构 + 本人逻辑推演**生成。代码必然存在瑕疵与纰漏，
但本人已亲测顺利通关全流程，核心的物理闭环体验无严重阻碍。

### 最大的技术妥协（为什么用相机而不是瞄准组件）

经过深度底层逻辑分析，目前方案读取的是**相机（Camera）绝对坐标**，
而非纯粹的**瞄准组件（Aim / FCS）逻辑坐标**。

原因极其硬核：在模拟器的动态内存分配机制下，瞄准组件的实例地址本就随机漂移；
更致命的是，**不同机体的瞄准配件（头部、躯干）在内存中是完全独立的实例对象**。
这意味着，如果想完美追踪瞄准组件，除非把游戏里所有配件的对应数据结构
全部解析出来，再写一套极其复杂的动态匹配规则 —— 否则换个配装、换台电脑，
地址直接报废。

相比之下，相机是玩家实体的**全局根组件**，跨配装相对稳定。
代价是：相机存在物理弹簧臂的视觉滞后，导致在极限微调时鼠标不够绝对精准。

> **给后来者的提示**：若有大佬能通过遍历玩家实体组件树（Component Tree）
> 完美动态定位任意 FCS 实例地址，本项目愿当场退役。

### 关于通用性

本项目的核心架构（内存数据结构解析 + 绝对坐标系映射 + PD 阻尼控制器）
理论上不局限于 ACVD，适用于任何面临类似视角控制困境的模拟器 3D 游戏。
